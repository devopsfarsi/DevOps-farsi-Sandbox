# User Flow

این سند مسیر کاربر را در DevOps Farsi Sandbox توضیح می‌دهد.

---

## نمای کلی

```
Login → Dashboard → Select Template → Create Sandbox → Workspace → Solve → Validation → Score → Cleanup
```

---

## 1. Login

کاربر وارد سایت می‌شود.
در نسخه اولیه فقط Name دریافت می‌شود و بدون رمز عبور وارد می‌شود.

نکته‌ها:

- در MVP هیچ اکانت واقعی وجود ندارد و شناسایی کاربر فقط بر اساس Name است.
- سیستم برای هر کاربر یک شناسه یکتا (User ID) تولید و ذخیره می‌کند تا Progress و Score او بعداً قابل پیگیری باشد.
- راه‌حل نهایی احراز هویت جزو [تصمیم‌های باز](08-open-decisions.md) است (D-009).

---

## 2. Dashboard

کاربر Templateهای موجود را می‌بیند.

Templateها بر اساس ویژگی‌های مختلف قابل فیلتر و دسته‌بندی هستند:

- Difficulty — easy / medium / hard
- Architecture — مثلاً Single Service یا Multi Service
- Technology — مثلاً Nginx، Docker، Kubernetes، Monitoring

هر Template همچنین این اطلاعات را نشان می‌دهد:

- شرح کوتاه سناریو
- Duration
- Skills

---

## 3. Select Template

کاربر یک Template انتخاب می‌کند و صفحه جزئیات آن را می‌بیند:

- شرح سناریو و مسئله
- لیست Taskها (بدون لو دادن راه‌حل)
- سطح دشواری، مدت زمان و مهارت‌های تمرین‌شده

---

## 4. Create Sandbox

Backend درخواست ساخت Sandbox را دریافت می‌کند.

وضعیت‌های ساخت:

- Queued — درخواست در صف انتظار است
- Creating — Sandbox در حال ساخته شدن است
- Ready — آماده ورود کاربر است

قواعد (اعداد پیشنهادی و قابل تغییر هستند):

- در MVP هر کاربر فقط **یک Sandbox فعال همزمان** می‌تواند داشته باشد.
- اگر ظرفیت سیستم پر باشد، درخواست در صف قرار می‌گیرد و کاربر موقعیت خود را می‌بیند.
- اگر ساخت بعد از حدود 2 دقیقه موفق نشد، پیام «ساخت ناموفق» نمایش داده می‌شود و کاربر می‌تواند دوباره تلاش کند.

---

## 5. Workspace

کاربر وارد محیط خود می‌شود و به این ابزارها دسترسی دارد:

- IDE — مشاهده و ویرایش فایل‌ها و Configuration
- Terminal — بررسی سرویس‌ها، Debug و اجرای دستورات محدود
- Monitoring — مشاهده Metrics، Logs و وضعیت سرویس‌ها

نحوه فنی اتصال به Workspace (دامنه اختصاصی، WebSocket، امنیت و ...) جزو [تصمیم‌های باز](08-open-decisions.md) است (D-008).

---

## 6. Solve

کاربر مشکل را حل می‌کند:

1. لیست Taskها را می‌بیند.
2. سیستم را بررسی و تغییرات لازم را اعمال می‌کند.
3. هر زمان بخواهد می‌تواند وضعیت فعلی را Validate کند.

---

## 7. Validation

سیستم به‌صورت خودکار چک‌های مرتبط با هر Task را اجرا می‌کند.

نمونه خروجی:

```
Task 1 — Check 1: PASS
Task 1 — Check 2: FAIL
Task 2 — Check 1: PASS
```

قواعد:

- Validation محدودیتی در دفعات اجرا ندارد؛ کاربر بعد از هر اصلاح می‌تواند دوباره امتحان کند.
- نتیجه هر Check جداگانه نمایش داده می‌شود تا کاربر بفهمد چه چیزی هنوز درست نشده است.
- Checkها هرگز راه‌حل را فاش نمی‌کنند.

---

## 8. Score

بعد از موفقیت یا اتمام زمان، نتیجه ثبت می‌شود:

- Score بر اساس تعداد Taskهای حل‌شده، زمان صرف‌شده و تعداد Hintهای استفاده‌شده محاسبه می‌شود. فرمول دقیق در فاز 2 نهایی می‌شود.
- Progress کاربر ذخیره می‌شود.

---

## 9. Cleanup

Sandbox در این حالت‌ها حذف می‌شود:

- کاربر تمرین را تمام کرده و Finish زده است.
- TTL تعریف‌شده در Template تمام شده است.
- Sandbox مدت طولانی بدون فعالیت رها شده و زمان انقضای آن رسیده است.

بعد از حذف، همه داده‌های داخل Sandbox پاک می‌شوند؛ اما Score و Progress کاربر بیرون از Sandbox نگهداری شده و باقی می‌مانند.

---

## حالت‌های خطا

| حالت | رفتار سیستم |
|------|-------------|
| ساخت Sandbox ناموفق بود | پیام خطا + امکان تلاش مجدد |
| ظرفیت سیستم پر است | قرار گرفتن در صف + نمایش موقعیت در صف |
| اتصال کاربر قطع می‌شود | Sandbox تا پایان TTL باقی می‌ماند و کاربر می‌تواند برگردد |
| TTL تمام می‌شود | حذف خودکار Sandbox + ثبت نتیجه فعلی |
| خطای داخلی سیستم | پیام مناسب به کاربر + ثبت در لاگ برای Debug |
