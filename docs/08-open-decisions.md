# تصمیم‌های باز (Open Decisions)

انتخاب‌های فنی مهم این پروژه به‌صورت باز و شفاف با مشارکت کامیونیتی گرفته می‌شود. این فایل ثبت رسمی تصمیم‌هاست (سبک سبک ADR).

---

## مکانیزم تصمیم‌گیری

1. برای هر تصمیم یک Issue با لیبل `decision` باز می‌شود.
2. گزینه‌ها با مزایا و معایب در ایشو بحث می‌شوند.
3. تصمیم نهایی با یک PR در همین فایل ثبت می‌شود و وضعیت به Decided تغییر می‌کند.

وضعیت‌ها:

- **Open** — هنوز تصمیم گرفته نشده
- **Proposed** — پیشنهاد مشخصی مطرح شده و در حال بررسی است
- **Decided** — نهایی شده

## تصمیم‌های باز

### D-003 — استک Backend
- **وضعیت:** Open
- **زمینه:** لایه API و کنترل سیستم
- **گزینه‌ها:** Python/FastAPI، Node.js/NestJS، Go، ...
- **پیشنهاد اولیه در دیاگرام:** FastAPI (Python)
- **معیار:** سادگی برای کانتربیوترها، اکوسیستم، تجربه تیم

### D-004 — استک Frontend
- **وضعیت:** Open
- **گزینه‌ها:** Next.js/React، Vue/Nuxt، ...
- **پیشنهاد اولیه در دیاگرام:** Next.js/React
- **معیار:** پشتیبانی از Workspace UI (Terminal و IDE)، جامعه کانتربیوترها

### D-005 — Database اصلی
- **وضعیت:** Open
- **پیشنهاد اولیه در دیاگرام:** PostgreSQL
- **معیار:** ذخیره کاربر، Template، Score و وضعیت Sandbox

### D-006 — Queue / Cache
- **وضعیت:** Open
- **پیشنهاد اولیه در دیاگرام:** Redis
- **معیار:** کارهای async مثل ساخت Sandbox و صف ظرفیت

### D-007 — Object Storage
- **وضعیت:** Open
- **پیشنهاد اولیه در دیاگرام:** MinIO / S3
- **سؤال اصلی:** آیا در MVP ضروری است یا به فازهای بعد موکول شود؟

### D-008 — دسترسی به Workspace (Terminal و IDE)
- **وضعیت:** Open
- **زمینه:** کاربر از مرورگر به IDE و Terminal داخل Sandbox وصل می‌شود
- **گزینه‌ها:** ابزارهای متن‌باز Web Terminal/Web IDE، راه‌حل‌های Self-hosted
- **معیار:** امنیت، تأخیر کم، مصرف منابع کم

### D-009 — احراز هویت (فازهای بعدی)
- **وضعیت:** Open — در MVP فقط Name بدون رمز است
- **گزینه‌ها:** GitHub OAuth، ایمیل، بدون رمز با شناسه دائمی
- **معیار:** جلوگیری از سوءاستفاده منابع بدون ایجاد سد ورود

### D-010 — هاست و هزینه زیرساخت
- **وضعیت:** Open
- **زمینه:** K3s کجا اجرا شود (VPS ابری، سرور اختصاصی، ترکیبی) و هزینه را چه کسی می‌پذیرد
- **معیار:** هزینه، دسترسی شبکه کاربران، پایداری

### D-011 — ظرفیت فاز 1
- **وضعیت:** Open
- **زمینه:** چند Sandbox همزمان پشتیبانی شود؛ سایز نود K3s؛ سقف Sandbox برای هر کاربر
- **پیشنهاد اولیه:** شروع با یک نود و سقف مشخص برای Sandboxهای همزمان

### D-012 — مکانیزم TTL و Cleanup
- **وضعیت:** Open
- **گزینه‌ها:** Scheduler در Backend، Controller در Kubernetes، ترکیبی

### D-013 — Stack مانیتورینگ
- **وضعیت:** Open
- **پیشنهاد اولیه در دیاگرام:** Prometheus + Loki + Grafana
- **معیار:** مصرف منابع، سادگی راه‌اندازی، تجربه کاربر

### D-014 — موتور Validation
- **وضعیت:** Open
- **زمینه:** اجرای Checkهای تعریف‌شده در template.yaml
- **گزینه‌ها:** جزئی در Backend، Jobهای Kubernetes، ابزارهای تست موجود

### D-015 — CI/CD
- **وضعیت:** Open
- **زمینه:** تست خودکار Templateها، Build و Deploy سیستم

### D-016 — ابزار تست محلی Templateها
- **وضعیت:** Open
- **گزینه‌ها:** k3d، kind، minikube
- **زمینه:** کانتربیوترهای Template باید قبل از PR بتوانند محلی تست کنند

### D-017 — استاندارد Commit و برنچ
- **وضعیت:** Open
- **پیشنهاد اولیه:** Conventional Commits + الگوی نام برنچ سند 06
